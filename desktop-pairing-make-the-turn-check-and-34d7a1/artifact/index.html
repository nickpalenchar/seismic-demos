A pairing abandoned by a switch stays abandoned

Connecting the desktop app to Seismic on another machine starts with the app checking the address, which can take a few seconds. If you switch workspaces during that check, the abandoned connection used to have a small window in which it could still take over: it sent the window to the other machine's pairing page and saved that machine as the active workspace, undoing your switch. Now the check of whether you moved on and the start of the pairing are a single step, so a switch always wins.

In the built app: switching while the address is checked

A debug build of the app, with "Mac Studio" a scratch Seismic behind a proxy that holds its answer for 8 seconds, and "Fast C" a second workspace that answers at once.

Checks

  • ok after the switch, the window stayed on Fast C
  • ok the abandoned pairing never sent the window to the pairing page
  • ok nothing was saved: Fast C active, Mac Studio not on the list
  • ok a pairing nothing interrupts still goes through to the pairing page and its result

What changed

  • The window's "turn" and the pairing under way now share one lock. A pairing starts only if the turn has not changed since its page read it, and starting it moves the turn on in the same step.
  • The start of the pairing and the move to its page happen on the app's main thread, where every switch, "New workspace" and delete also runs. A switch made while the address is checked comes first and ends the attempt. A switch made later comes after it and takes the window elsewhere.
  • The pairing remembers the turn it started in. Its result counts only while that turn lasts, not the turn at the moment its page loaded.
  • A new unit test covers these rules.

The original race was a gap of microseconds between two steps, so a live run shows the same outcome before and after the change. The live run confirms that the reworked path still behaves right end to end. The unit test covers the rule that closes the gap.
